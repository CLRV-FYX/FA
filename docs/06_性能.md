# FA 性能实测

测试环境：x86-64 Linux（Debian 13），2 核 Xeon @ 2.6GHz。
对比对象：**gcc -O2**（C 的性能天花板）与 **CPython 3.13**。
FA 使用默认优化级别 `-O 2`。所有结果均经过与 C 版本**逐位比对校验**。

复现方法：

```bash
cd bench && python3 run_bench.py
```

---

## 结果总览

| 基准测试 | FA | C (gcc -O2) | Python 3.13 | FA 相对 C | FA 相对 Python |
|---|---|---|---|---|---|
| `fib(38)` 密集递归 | **137 ms** | 46 ms | 3.30 s | 慢 **3.0 倍** | **快 24 倍** |
| 1 亿次算术循环 | **62 ms** | 53 ms | 13.8 s | 慢 **1.17 倍** | **快 220 倍** |
| 200 万内素数筛 | **11 ms** | 6.5 ms | 122 ms | 慢 **1.75 倍** | **快 11 倍** |

> 上一轮（m5）的基线是 301 / 122 / 41 ms，对应 4.43 / 1.42 / 4.73 倍。
> 素数筛从「慢 4.5 倍」降到「慢 1.75 倍」，主要来自**窄元素紧凑存储**：
> `Vec<bool>` 原本每个元素占 8 字节，内存流量是 C 的 `char[]` 的 8 倍。

> 表格里 FA 与 C 的耗时区间来自多次重复测量（机器负载会波动）；
> 结论稳定：**FA 与 gcc -O2 在同一数量级，比 CPython 快一个到两个数量级。**

## 1. 算术循环 —— FA 最接近 C 的场景

```fa
fn main() -> i64:
    let s: i64 = 0
    let i: i64 = 0
    while i < 100000000:
        s = s + i * 3 - i / 2
        i = i + 1
    print(s)
    return 0
```

生成的汇编（热循环，无一次内存访问）：

```asm
    .p2align 4                  ; 循环头对齐到 16 字节
.fa_main_while1:
    cmp   r11, 100000000
    jge   .fa_main_wend3        ; 条件取反，落进循环体（省掉一条 jmp）
.fa_main_wbody2:
    mov   r12, r11              ; i
    imul  r12, 3
    mov   r13, r10              ; s
    add   r13, r12
    mov   rcx, r11              ; i/2 -> 移位（除以 2 的幂，避开 idiv）
    sar   rcx, 63
    and   rcx, 1
    add   rcx, r11
    sar   rcx, 1
    mov   r14, rcx
    mov   r10, r13
    sub   r10, r14
    add   r11, 1
    jmp   .fa_main_while1
```

**62 ms / 1 亿次 ≈ 0.62 ns 每次迭代**。

## 2. 为什么 FA 能这么快

1. **直接生成机器码**，没有虚拟机、没有字节码解释、没有 JIT 预热。
2. **变量留在寄存器里**：线性扫描寄存器分配 + 精确的循环活性区间分析，
   循环变量不会被无谓地溢出到栈上。
3. **复制合并**：`MOV/BIN/UN` 里"源值用完即死"的目标直接复用源的寄存器，
   大量 `mov r, r` 消失，活跃值变少 → 需要保存的被调用者寄存器也变少
   （`fib` 的函数开场从 5 次 push 降到 3 次）。
4. **寄存器池分类**：跨调用存活的值优先分配被调用者保存寄存器（免得每次调用都 save/restore），
   不跨调用的值优先分配 `r10/r11`（免得函数开头 push）。
5. **容器访问内联**：`v.get(i)` / `v.set(i, x)` / `len(v)` 不再走函数调用，
   直接展开成「越界检查 + 一条 mov」（素数筛因此快了 1.5 倍）。
6. **窥孔优化**：
   - `cmp + setcc + movzx + test + jne` → `cmp + jl`（一次省 4 条指令）
   - 除以 2 的幂 → 移位（避开 `idiv` 的 20+ 周期延迟）
   - 消除 `mov r, r` 之类冗余搬运
7. **循环头 16 字节对齐**（`compiler/falang/asmgen.py`，与 gcc `-falign-loops` 同思路）。
   同一段循环仅仅因为起始地址不同，实测可以差 **40% 以上**：
   取指与解码单元按 16/32 字节的窗口工作，跨窗口的循环头会持续掉速。
8. **分支布局**：条件跳转的两个出口里，如果真分支就是下一条指令，
   就把条件取反、只保留一条跳转；相邻标签会被合并，
   「跳到下一条指令」的 `jmp` 直接删掉。热循环每轮省 1~2 条被执行到的跳转。
9. **循环不变量外提（LICM）**（`compiler/falang/opt.py`）：
   用回边识别循环，按「定义点 + 别名分析」判定不变的计算，搬到循环前的前插块。
   素数筛内层的 `flags.len` 与 `flags.data` 因此每轮少两次内存读取。
10. **目标驱动代码生成**：`x = x + 1` 直接生成 `add`，
    不再「算到新临时寄存器再搬回去」。每条赋值省 1~2 条 `mov`。
11. **比例变址寻址**：`v.get(i)` / `v.set(i, x)` 直接生成 `[data + i*8]`，
    省掉一条 `imul`。
12. **调用结果留在 rax**：若返回值只被紧邻的下一条指令用一次，
    就不搬到被调用者保存寄存器（`fib` 因此少一次 push/pop）。
13. **窄元素紧凑存储**：`Vec<bool>` / `Vec<u8>` / `Vec<i8>` / `Vec<char>` 每元素 1 字节，
    `i16/u16` 2 字节、`i32/u32` 4 字节（对外传值仍是 64 位）。
    这是素数筛提速的主要来源。
14. **省掉多余的 `mov eax, 0`**：`al` 只在可变参数调用里有意义，
    已知被调函数不是可变参数时就不生成（gcc 也不生成）。
15. **加减常量折叠成 `lea`**：`x - 2` 用一条 `lea r, [x-2]`，省掉一条 `mov`。
16. **运行时用 `write()` 系统调用直写**，I/O 不走 stdio 的锁。
17. **栈帧严格按 SysV ABI 对齐**，调用 libc 时不会触发未对齐的慢路径。

## 3. 与 Python 对比时最值得注意的一点

Python 里`s = s + i*3 - i//2` 每循环一次都要做对象分配与类型分派；
FA 里是**三条机器指令**。所以纯计算场景下差距是 **50 ~ 180 倍**。

反过来，如果你的 Python 代码本来就是 `numpy.sum(a)` 这种
"一次调用干完所有活"的写法，那么用 `use py` 调 numpy 会更快 ——
**FA 的定位不是取代 numpy，而是让你在同一门语言里**
**既能写出 numpy 级别快的热点，又能直接调 numpy。**

## 4. 性能建议

- 热点循环里避免跨语言调用（每次 `py.eval` / `java.call_*` 有微秒级开销）。
- 需要极致的场景用 `asm """..."""` 插入手写汇编。
- 定长数组 `[T; N]` 比 `Vec<T>` 快（少一层间接和引用计数）。
- 大结构体传参建议传指针（`*Point`），避免拷贝。
- 用 `fa asm x.fa` 看看生成的汇编，往往一眼就能发现瓶颈。

## 5. `fib` 为什么还是慢 3 倍

`fib(38)` 会做 **1.26 亿次**递归调用（已用计数器核对，C 与 FA 调用次数完全相同），
所以这个基准测的其实是**每次函数调用的固定开销**，而不是算术能力。

| | 每次调用大约 |
|---|---|
| C (gcc -O2) | ~0.46 ns |
| FA | ~1.09 ns |

FA 每次调用的指令数已经从 29 条压到 21 条，剩下的差距主要来自：

- gcc 默认 `-fomit-frame-pointer`，FA 还在用 `rbp` 做帧指针（多 3 条指令）。
- 递归里必须把 `n` 与上一步的结果放在被调用者保存寄存器里（多 2 次 push/pop）。

**结论**：如果你的程序是「少量计算 + 海量函数调用」，FA 会比 C 慢 2~3 倍；
如果是循环里做实事，差距在 1.2 倍以内（见上面的算术循环）。
这也是为什么把 `fib` 留在基准里——它诚实地暴露了 FA 目前最弱的一环。

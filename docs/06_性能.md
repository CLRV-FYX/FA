# FA 性能实测

测试环境（`python3 bench/run_bench.py` 会把机器信息打在表头）：

| 项 | 值 |
|---|---|
| CPU | Intel(R) Xeon(R) Processor @ 2.60GHz，2 核（虚拟机，共享宿主） |
| 内核 | Linux 6.1.158+ x86-64 |
| C 编译器 | gcc (Debian 12.2.0-14+deb12u1) 12.2.0，`-O2` |
| Python | CPython 3.11.2 |
| FA | `-O 2`（默认） |

所有结果都与 C 版本**逐字节比对校验**过（输出不一致就不算成绩）。

复现：

```bash
python3 bench/run_bench.py                 # 每个基准跑 5 次取最小值
python3 bench/run_bench.py --repeat 9      # 想更稳一点
python3 bench/run_bench.py fib             # 只跑 fib
python3 bench/run_bench.py --java          # 额外测 JVM（需要 JDK）
```

> 这个脚本**每次都从源码重新构建** FA 与 C 两个版本，产物放在临时目录。
> （以前它只运行 `bench/` 下已经存在的 `fa_fib` / `c_fib`：全新克隆里根本没有
> 这些文件，直接 `FileNotFoundError`；本地残留旧二进制时，测出来的还是某个
> 历史版本的成绩。）

## 结果总览（本机实测，2026-09）

| 基准测试 | FA | C (gcc -O2) | C「同算法」 | CPython | FA/C | FA/C 同算法 | FA vs Python |
|---|---|---|---|---|---|---|---|
| `fib(38)` 密集递归 | **292.7 ms** | 70.1 ms | 110.9 ms | 5151 ms | 4.17x | **2.64x** | 快 17.6 倍 |
| 1 亿次算术循环 | **94.4 ms** | 86.1 ms | 86.5 ms | 15801 ms | 1.10x | **1.09x** | 快 167 倍 |
| 200 万内素数筛 | **18.6 ms** | 8.3 ms | 8.5 ms | 120 ms | 2.25x | **2.19x** | 快 6.4 倍 |

**绝对毫秒数会随机器和负载变化**（这台是共享虚拟机，同样的代码在独占物理机上
大约快一倍）；要看的是**比值**，以及比值背后的原因。

## 1. 「C 同算法」这一列是干什么的

`gcc -O2` 对 `fib` 做了一件很关键的事：**把这个小递归函数内联进它自己**，
然后做公共子表达式消除 ——

```c
fib(n) = fib(n-1) + fib(n-2)
       = [fib(n-2) + fib(n-3)] + [fib(n-3) + fib(n-4)]
```

`fib(n-3)` 只算一次。实际生成的代码里，递归调用变成了 `fib(n-3)`、`fib(n-4)`、
`fib(n-5)` 的组合（`objdump -d` 可以直接看到），**调用次数少了一个量级**：

| gcc -O2 配置 | fib(38) | 说明 |
|---|---|---|
| 默认 | 70 ms | 递归内联 + CSE，干的活变少了 |
| `-fno-optimize-sibling-calls` | 5 ms | 连尾递归一起重排，进一步特化 |
| `-fno-inline` | **111 ms** | **和 FA 做同样多的递归调用** |

所以 `FA/C = 4.17x` 这个数字里，有相当一部分是「gcc 换了个算法」，
不是「同样的活 FA 干得慢 4 倍」。`-fno-inline` 那一列才是同算法对比：**2.64 倍**。
（`-fno-inline` 对另外两个基准几乎没影响：86.1→86.5 ms、8.3→8.5 ms，
因为它们没有递归可内联。）

FA 目前没有跨函数的递归特化 / CSE，这是路线图上的一项（见文末）。

## 2. 算术循环 —— FA 最接近 C 的场景

```fa
fn main() -> i64:
    let s: i64 = 0
    let i: i64 = 0
    while i < 100000000:
        s = s + i * 3 - i / 2
        i = i + 1
    print(s)
    return 0
```

生成的热循环（`fa asm loop.fa`，一次内存访问都没有）：

```asm
    .p2align 5                  ; 循环头对齐到 32 字节
.fa_main_while1:
    cmp   r11, 100000000
    jge   .fa_main_wend3        ; 条件取反，落进循环体（省掉一条 jmp）
.fa_main_wbody2:
    mov   r12, r11              ; i
    imul  r12, 3
    mov   r13, r10              ; s
    add   r13, r12
    mov   rcx, r11              ; i/2 -> 移位（除以 2 的幂，避开 idiv）
    sar   rcx, 63
    and   rcx, 1
    add   rcx, r11
    sar   rcx, 1
    mov   r14, rcx
    mov   r10, r13
    sub   r10, r14
    lea   r11, [r11+1]
    jmp   .fa_main_while1
```

**94 ms / 1 亿次 ≈ 0.94 ns 每次迭代**（gcc -O2 是 0.86 ns）。

### 循环头对齐：16 字节不够，要 32 字节

同一段循环，**只因起始地址不同就能差 40%**。这台机器上的实测：

| `.p2align` | 1 亿次算术循环 | 相对 gcc -O2 |
|---|---|---|
| 4（16 字节，旧值） | 123 ms | 1.43x |
| **5（32 字节，现值）** | **94 ms** | **1.09x** |
| 6（64 字节） | 104 ms | 1.22x |

原因是 Intel 的 uop cache（DSB）以 **32 字节**为窗口：循环头落在窗口中间时，
前端会退回传统译码路径。64 字节对齐没有额外收益，还白占 icache。
（`compiler/falang/asmgen.py` 里 `LABEL` 的处理，注释记了这组数字。）

> 这也是为什么改运行时 C 代码会让「纯计算」的基准变慢 30%：
> 运行时 `.o` 变大 → FA 代码在最终可执行文件里的地址平移 → 循环头掉到
> 不好的相位上。对齐到 32 字节之后，这种「隔墙打牛」式的抖动小了很多。

## 3. 为什么 FA 能这么快

1. **直接生成机器码**，没有虚拟机、没有字节码解释、没有 JIT 预热。
2. **变量留在寄存器里**：线性扫描寄存器分配 + 精确的循环活性区间分析，
   循环变量不会被无谓地溢出到栈上。
3. **复制合并**：`MOV/BIN/UN` 里「源值用完即死」的目标直接复用源的寄存器，
   大量 `mov r, r` 消失，活跃值变少 → 需要保存的被调用者寄存器也变少。
4. **寄存器池分类**：跨调用存活的值优先分配被调用者保存寄存器（免得每次调用都
   save/restore），不跨调用的值优先分配 `r10/r11`（免得函数开头 push）。
5. **容器访问内联**：`v.get(i)` / `v.set(i, x)` / `len(v)` 不走函数调用，
   直接展开成「越界检查 + 一条 mov」（素数筛因此快了 1.5 倍）。
6. **窥孔优化**：
   - `cmp + setcc + movzx + test + jne` → `cmp + jl`（一次省 4 条指令）
   - 除以 2 的幂 → 移位（避开 `idiv` 的 20+ 周期延迟）
   - 消除 `mov r, r` 之类冗余搬运
7. **循环头 32 字节对齐**（见上一节）。
8. **分支布局**：条件跳转的两个出口里，如果真分支就是下一条指令，
   就把条件取反、只保留一条跳转；相邻标签会被合并，
   「跳到下一条指令」的 `jmp` 直接删掉。
9. **循环不变量外提（LICM）**（`compiler/falang/opt.py`）：
   用回边识别循环，按「定义点 + 别名分析」判定不变的计算，搬到循环前的前插块。
   素数筛内层的 `flags.len` 与 `flags.data` 因此每轮少两次内存读取。
10. **目标驱动代码生成**：`x = x + 1` 直接生成 `add`/`lea`，
    不再「算到新临时寄存器再搬回去」。
11. **比例变址寻址**：`v.get(i)` / `v.set(i, x)` 直接生成 `[data + i*8]`，省掉 `imul`。
12. **调用结果留在 rax**：若返回值只被紧邻的下一条指令用一次，
    就不搬到被调用者保存寄存器。
13. **窄元素紧凑存储**：`Vec<bool>` / `Vec<u8>` / `Vec<i8>` / `Vec<char>` 每元素 1 字节，
    `i16/u16` 2 字节、`i32/u32` 4 字节（对外传值仍是 64 位）。
14. **省掉多余的 `mov eax, 0`**：`al` 只在可变参数调用里有意义。
15. **加减常量折叠成 `lea`**。
16. **运行时用 `write()` 系统调用直写**，I/O 不走 stdio 的锁。
17. **栈帧严格按 SysV ABI 对齐**，调用 libc 时不会触发未对齐的慢路径。

## 4. 引用计数要花钱，但只花在聚合值上

FA 是自动内存管理（编译期插入引用计数），这会让人担心「每个值都要 inc/dec」。
实际规则是：

- **标量（整数 / 浮点 / bool / char / 指针）完全不插任何指令** —— 上面那个
  1 亿次循环里没有一条引用计数指令，所以才能到 gcc 的 1.09 倍。
- **`str` / `Vec` / `Map`**：每次拷贝一条 `fa_rc_inc`，每次作用域结束一条 `fa_rc_dec`。
- **`struct` / `enum`**：只有**含有**引用计数字段时才生成 `__fa_drop_<T>` /
  `__fa_retain_<T>`；纯数据结构体（例如 `struct Q { n: i64, m: i64 }`）
  一次调用都不插，拷贝就是一条 `memcpy`。
- 容器里的结构体元素一律装箱，装箱/拆箱各一次 `malloc`/`free`。

代价换的是：`let b = a` 之后两份值各自独立、作用域结束自动释放，
没有 double free，也没有泄漏（`tests/cases/029_memory.fa` 在 300 MB 虚拟内存上限下
跑 20 万次「造结构体 + Vec + Map + 提前 return」，正常结束）。

## 5. 与 Python 对比时最值得注意的一点

Python 里 `s = s + i*3 - i//2` 每循环一次都要做对象分配与类型分派；
FA 里是**几条机器指令**。所以纯计算场景下差距是 **6 ~ 170 倍**（视基准而定）。

反过来，如果你的 Python 代码本来就是 `numpy.sum(a)` 这种
「一次调用干完所有活」的写法，那么用 `use py` 调 numpy 会更快 ——
**FA 的定位不是取代 numpy，而是让你在同一门语言里**
**既能写出 numpy 级别快的热点，又能直接调 numpy。**

## 6. 性能建议

- 热点循环里避免跨语言调用（每次 `py.eval` / `java.call_*` 有微秒级开销）。
- 需要极致的场景用 `asm """..."""` 插入手写汇编。
- 定长数组 `[T; N]` 比 `Vec<T>` 快（少一层间接和引用计数）。
- 大结构体传参建议传指针（`*Point`），避免拷贝。
- 深递归改成显式栈或循环：FA 还没有尾调用优化。
- 用 `fa asm x.fa` 看看生成的汇编，往往一眼就能发现瓶颈。

## 7. `fib` 每次调用还差在哪

`fib(38)` 会做 **1.26 亿次**递归调用，所以这个基准测的是
**每次函数调用的固定开销**，不是算术能力。

FA 生成的 `fa_fib`（21 条指令，含开场/收尾）：

```asm
fa_fib:
    push rbp
    mov  rbp, rsp
    push rbx
    push r12
    push r13                 ; <-- 推了但函数体里根本没用到
    sub  rsp, 40             ; <-- 其中 8 字节是给调用点保存用的溢出槽
    mov  rbx, rdi
    cmp  rbx, 2
    jge  .fa_fib_elif3
.fa_fib_ifbody2:
    mov  rax, rbx            ; 递归基：return n
    lea  rsp, [rbp-16]
    pop  r12
    pop  rbx
    pop  rbp
    ret
.fa_fib_elif3:
    lea  r11, [rbx-1]
    mov  rdi, r11            ; <-- 可以直接 lea rdi, [rbx-1]
    call fa_fib
    mov  r12, rax
    lea  rbx, [rbx-2]
    mov  rdi, rbx
    call fa_fib
    add  r12, rax
    mov  rax, r12
    lea  rsp, [rbp-16]
    pop  r12
    pop  rbx
    pop  rbp
    ret
```

（`fa asm bench/fib.fa` 的原始输出，只加了注释。）

还可以再省的（都在路线图上）：

- **帧指针**：FA 保留 `rbp`，gcc 默认 `-fomit-frame-pointer`（多 3 条指令）。
- **多推了一个被调用者保存寄存器**：`r13` 被 push/pop 但函数体里没用到，
  说明寄存器分配的活跃区间还偏保守。
- **`lea r11,[rbx-1]; mov rdi,r11`** 可以直接 `lea rdi,[rbx-1]`（少一条 mov）。
- **跨调用溢出**：`sub rsp, 40` 里有 8 字节是给调用点保存用的，
  如果活性分析更准就能省掉。
- **递归内联 + CSE**：gcc 靠这个把调用次数砍掉一个量级（见第 1 节），FA 还没有。

**结论**：「少量计算 + 海量函数调用」的程序，FA 比 C 慢 2.6 倍左右（同算法）；
循环里做实事的程序，差距在 **1.1 倍**以内。
把 `fib` 留在基准里，就是为了诚实地暴露 FA 目前最弱的一环。
